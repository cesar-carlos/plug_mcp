## Escopo e permissões mínimas — 2026-10-14

Firebird removido do suporte por decisão do produto. O candidato passa a exigir
PostgreSQL, SQL Server e SQL Anywhere; nenhum gate foi marcado completo.
O runner `plug_agente/tool/homologation/source_identity_permissions_test.dart`
passou 3/3 testes em fixture privada `se7e_persona_52383892c7b9_test`: identidade
com usuário restrito, leitura negada antes do grant, SELECT permitido após grant,
INSERT/UPDATE/DELETE/ALTER/DROP negados e SELECT negado após revoke. A identidade
permaneceu igual. PostgreSQL recebeu EXECUTE em pg_control_system; SQL Anywhere,
SELECT no marcador provisionado. SQL Server não recebeu role administrativa.
Isso não prova substituição de base, revogação em trânsito, restauração DBA,
publicação genérica ou aceite operacional. Produção permanece bloqueada.

A matriz ODBC de operações do mesmo candidato passou 57/57 casos nos três
motores, com SQL compilado pelo MCP, executor e journal reais: identidade e
estrutura na conexão, parâmetros/outputs, commit/rollback, duplicatas, revogação
e resultado incerto sem replay. É evidência do harness de operações, não do
runner genérico de publicação nem de aceite integral da cadeia.

## Publicação SQL genérica e células nulas — 2026-10-14

Coordenada com a frente de adoção compartilhada, sem execução Flutter concorrente.
Bases Git: agente `fdb44d86b2a36df85c0133cf72167217fc1bd16e`,
MCP `136b5bfc8f7104b753bbd3703c9ffda196fdd51f`,

- Após identificar o runner no relatório e recusar `input.operationId` fixo:

- Agente: **33/33** testes de saneamento/transporte/consulta verificada; análise

Comando completo: `scripts/with-project-node.ps1 node node_modules/vitest/vitest.mjs
run --config vitest.persona-chain.config.ts`, com PERSONA_CHAIN_MANIFEST e
FLUTTER_BIN explicitamente vinculados à fixture. Na rodada final dirigida foi
acrescentado `-t SQL.gen`. O wrapper operacional equivalente e os pré-requisitos
estão em [cadeia isolada](homologation-chain.md).

As tentativas anteriores recusaram fonte obtida da representação administrativa
em vez do vínculo persistido e depois detectaram perda de células SQL `null` no
saneamento do wire. O teste de nulidade falhou antes da correção; o envelope
nativo com row_count e os múltiplos resultados agora preservam essas células.
No diagnóstico nativo, as operações concluíam com duas linhas afetadas, mas o
campo marker nulo desaparecia na resposta. O rollback manteve ambas as tabelas.
Nenhum desses resultados reprovados foi tratado como aprovação.

Escopo comprovado: consultas parametrizadas com dados e vazias, Unicode,
inteiros, null, gravação em duas tabelas, rollback por versão divergente,
publicação pelo catálogo real, revalidação de pacote/fonte/casos e relatório.
Limites: dados sintéticos, usuário de fixture com DDL local, tabela privada
publication_*, sem certificação integral de tipos/collations/triggers,
SQL adaptável/conciliável genérico, adoção compartilhada pelo novo executor ou
composição operacional final. O enforcement desconhecido do SQL Anywhere
continua impedindo adoção de constraints. Nenhum gate foi concluído; ready=false
e completedGates vazio nos três projetos. Não autoriza instalador/appcast.
