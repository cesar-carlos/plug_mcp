## Rodada 2026-10-10: drivers reais e gates de runtime/contrato

**48 testes reais passaram, 12 por motor, sem skips.** O runner usa `odbc_fast`
5.0.1, factory/transação de produção, decoder RPC e journal Drift em arquivos
SQLite próprios. As bases foram criadas exclusivamente para esta rodada.

| Motor           | Versão testada | Driver ODBC                   |
| --------------- | -------------- | ----------------------------- |
| PostgreSQL      | 17.11          | psqlODBC Unicode 18.00.0000   |
| SQL Server 2022 | 16.0.4236.2    | Microsoft 18.06.0001          |
| SQL Anywhere    | 16.0.0.2043    | SAP 16.00.2043                |
| Firebird        | 5.0.4          | Firebird/InterBase 02.00.0156 |

Inclui comandos INSERT/UPDATE/DELETE compilados pelo MCP, parâmetros tipados,
contagem direta, commit, rollback de todas as etapas após excesso de linhas ou
conflito de versão, revogação antes do commit, passagem de ID gerado como parâmetro,
duplicatas e journal fechado/reaberto. No caso de confirmação perdida, o commit
ODBC é real e somente a perda da resposta é injetada; o estado permanece desconhecido
e a segunda chamada não reexecuta. A autoridade do runner é sintética: isso não
certifica JWT Client, vínculo/policy ou o fluxo HTTP/Socket completo nesses motores.

A homologação encontrou e corrigiu:

- `SQL_ATTR_CURRENT_CATALOG` vazio/truncado nos drivers PostgreSQL, SQL Anywhere
  e Firebird. O agente agora prova a base com SELECT fixo de metadados, completo,
  na conexão dedicada, antes de iniciar a transação. Nomes são comparados exatamente;
  somente caminhos Windows absolutos Firebird normalizam separador/caixa.
- `DBN={nome}` recusado pelo SQL Anywhere. O vínculo usa valor já validado contra
  injeção de atributos, sem alterar senha delimitada ou destino da conexão.
- Escritas PostgreSQL/Firebird sem outputs não produziam `RETURNING`. O compilador
  acrescenta `RETURNING 1 AS "__operation_row"` após validar a adaptação, sem ler
  coluna de negócio extra. O hash preparado inclui essa instrução.
- A prova de identidade e as contagens internas integram o teto de 32 comandos.

Node **24.21.0** foi baixado do distribuidor oficial e conferido pelo SHA-256;
os requisitos >=24.21.0 <25 permanecem. Instalação e PATH globais foram preservados.
No Windows, prepare o runtime com `scripts/install-project-node.ps1` e execute
`scripts/with-project-node.ps1 npm.cmd run release:check`.

O contrato do hub passou para **1.3.0**, incluindo somente GET autenticado de
`/client-auth/me` e descrevendo corretamente `sql.operation.*` condicionado à
capability v1. Geração, baseline aditivo e 53 testes de contrato passaram.
`training:check` fixa os bytes do contrato e de
`contracts/hub-persona-v2.snapshot.patch`. A referência é **commit-base + patch
revisado**, não uma alegação de que o commit antigo contém as alterações locais.
A reprodução em uma cópia limpa do commit-base passou em `contract:check`.
CI aplica o mesmo patch antes de verificar o hub. A base comum foi versionada;
publicações/relatórios com hash anterior precisam de revalidação.

Os testes abaixo são históricos. Esta rodada não libera o aceite integral:
SELECT adaptável Firebird, outputs gerados de escrita publicados no SQL Anywhere,
matriz completa de tipos/triggers/condições, transporte com autoridade real nos
quatro motores, integrações, OAuth/console v2, retenção e corte seguem pendentes.
Os três manifestos continuam `ready:false`, sem gates integrais marcados.

Verificações locais finais: `release:check` do MCP passou com Node 24.21.0 e
TypeScript 7.0.2, incluindo lint, formatação, tipos, build, **1.043 testes backend
aprovados** (91 skips legados) e **19 testes do console legado**, lint/tipos/build

Isso não revalida a suíte Prisma completa do hub nem certifica o console v2.
PostgreSQL persona-v2: **63 testes passaram**, quatro arquivos, sem skips,

Após os testes, os dois contêineres dedicados, o processo SQL Anywhere, os arquivos

### Reproduzir a matriz obrigatória

Crie bancos exclusivos com identidade `se7e_persona_<12 hex>_test`; PostgreSQL e
SQL Server em contêineres próprios com portas loopback aleatórias, SQL Anywhere
em processo próprio e Firebird em arquivo próprio. Nunca utilize DSNs existentes,
fontes cadastradas ou `.env` operacional. O manifesto privado contém `runId`,
`root` (diretório de mesmo nome) e `engines.postgres|mssql|sybase|firebird`, cada um
com `database` e `connectionString`. Os três nomes de banco devem ser `runId`;
Firebird deve ser `<root>/<runId>.fdb`. Guarde o manifesto fora do Git e restrinja
seu acesso; contém somente credenciais descartáveis desses ambientes.

Execute `scripts/run-four-engine-homologation.ps1 -Manifest <manifesto privado>
-Flutter <flutter.bat> -DriverDirectories <diretórios locais dos drivers>`.
O script compila fixtures com o MCP e chama explicitamente
`plug_agente/tool/homologation/sql_operation_four_engines_test.dart`. Ausência de
manifesto, motor, driver ou conexão reprova; não há fallback ou skip. O runner
recria apenas `operation_fixture` nos bancos explicitamente identificados e usa
um journal novo por teste. Limpe exclusivamente contêineres/processos/arquivos e
eventuais DSNs temporários que você criou, após conferir suas identidades.

Hot reload não foi validado: descoberta DTD sem app ativo e revisão automática
recusou recarregar um aplicativo não identificado. Nenhum app operacional foi iniciado.
